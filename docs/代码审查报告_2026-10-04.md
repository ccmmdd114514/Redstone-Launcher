# 红石启动器 代码审查报告

> 日期：2026-10-04
> 审查范围：`src/` 下全部 8 个源码文件（main / args / install / java / launch / meta / net / paths）
> 审查目的：0.9.0-beta.4 发布后的缺陷排查，为 0.9.0-beta.5 的修复范围提供依据
> 方法：静态通读 + 控制流分析，未运行目标程序

## 结论摘要

本次共发现 **2 个高危缺陷、7 个中等缺陷、4 类边界缺陷**。
其中「版本号参数未校验导致路径穿越」可造成不可逆的数据损坏，建议在下一个版本优先修复。
另有若干模块经检查确认无问题，已在文末列出，避免重复排查。

## 高危

### H1. 版本号参数未校验直接拼接路径，可导致任意目录被删除

- 位置：`paths.rs:46`、`paths.rs:54-68`、`main.rs:122`、`main.rs:139`、`install.rs:160`、
  `launch.rs:118`、`launch.rs:209`
- 问题：`version` 直接来自命令行/交互模式的位置参数，未经任何校验就交给 `PathBuf::join`。
  Rust 的 `join` 有两个关键语义：遇到绝对路径会整体替换原路径；`..` 不会被拦截。
- 触发条件：
  - `redstone remove --yes "C:\Users\<用户名>\Documents"` —— 实例目录判断命中后递归删除该目录；
  - `redstone remove --yes "..\..\..\..\某目录"` —— 穿越到实例区之外；
  - `redstone install "..\..\out"` —— 在共享区之外递归创建目录。
- 影响：任意已存在目录被递归删除（不可逆）。注意 `remove` 命令不经过版本清单校验，
  无法被清单查询兜住，此路径可直接利用。
- 建议：在 `paths` 的入口对 `id` 做白名单校验（例如 `^[A-Za-z0-9._-]{1,64}$`，
  并显式拒绝 `.`、`..`、含路径分隔符或盘符的输入），或用 `Path::components()`
  断言所有组件均为 `Component::Normal`。

### H2. `split_libraries` 在空 URL 原生库处提前返回，截断整个 classpath

- 位置：`install.rs:42-51`（关键分支在 `install.rs:44-46`）
- 问题：遇到原生库且其 `artifact.url` 为空时执行 `return (classpath, natives)`，
  直接结束整个循环；同一文件的 `library_items`（`install.rs:73-86`）在同类场景用的是
  `continue`，可确认此处为笔误。
- 触发条件：版本清单中任一原生库的 `artifact.url` 为空。
- 影响：该库之后的所有库与原生库被一并丢弃，classpath 残缺，
  启动时报 `ClassNotFoundException` / `UnsatisfiedLinkError`；
  而安装阶段显示成功，问题只在启动时暴露。
- 建议：将该处 `return` 改为 `continue`。

## 中等

### M1. 版本元数据缺少完整性校验，且 `artifact.path` 未校验

- 位置：`meta.rs:14-20`、`install.rs:13-28`、`meta.rs:171-186`、`install.rs:57/80/96`
- 问题：版本清单与 `version.json` 全程只走 `http.json` 拉取，从不校验 sha1；
  `artifact.path` 又被原样拼接到 `libraries_dir()`。
- 触发条件：使用第三方镜像，或超出 HTTPS 信任范围时，清单被篡改。
- 影响：可写入任意位置的文件；配合 `install.rs:145/150` 的哈希切片还可能触发崩溃（见 L1）。
- 建议：解析清单时保留每个版本的 `sha1/size` 并校验 `version.json`；
  对 `artifact.path` 施加与 H1 相同的路径组件白名单。

### M2. 离线 UUID 与官方及主流启动器不兼容

- 位置：`launch.rs:12-20`
- 问题：当前使用 `uuid5(NAMESPACE_URL, "offline:{name}")`。官方与多数第三方启动器的
  离线 UUID 为 `UUID.nameUUIDFromBytes(("OfflinePlayer:" + name))`，
  即无命名空间的 v3（MD5），前缀为 `OfflinePlayer:`。
- 触发条件：玩家曾用其他启动器在同一离线服务器游玩。
- 影响：同一昵称得到不同 UUID，服务器视为不同玩家，存档与权限不互通。
- 建议：改用官方算法；若不要求互通，需在 README 明确声明。

### M3. `rules` 求值忽略 `os.version`

- 位置：`args.rs:116-139`、`meta.rs:104-108`
- 问题：`rule_matches` 只判断 `os.name` 与 `os.arch`，`os.version` 被反序列化后从未参与判定。
- 影响：含 `os.version` 条件的规则一律按命中处理，可能与官方启动器行为不一致。
- 建议：读取 `os.version` 并与当前系统版本对照，或在代码中注明有意忽略及其理由。

### M4. 版本清单地址不支持镜像回退

- 位置：`net.rs:35-56`、`install.rs:14`
- 问题：`MANIFEST_URL` 不匹配 `to_bmclapi` 的任何分支，候选地址恒为单元素，永不回退镜像。
- 触发条件：选择 `--mirror bmclapi` 但官方清单不可达。
- 影响：镜像在起步阶段形同失效，用户在不知情的情况下直接失败。
- 建议：为清单地址补充 BMCLAPI 端点映射。

### M5. 进程锁以全局 java PID 判定，存在 PID 复用误判

- 位置：`launch.rs:164-175`、`launch.rs:139-157`
- 问题：`java_pids()` 收集全机所有 `java.exe` / `javaw.exe` 的 PID，仅做包含判断；
  若锁文件中的旧 PID 被无关 java 进程复用，会误判为「正在运行」而拒绝启动。
- 影响：无法启动且提示信息误导；跨用户、跨会话亦会互相影响。
- 建议：锁文件同时记录 java 可执行路径或启动时间，用启动时间复核 PID 归属。

### M6. 旧版 `minecraftArguments` 分支会产生悬空参数

- 位置：`launch.rs:85-103`、`args.rs:93-99`、`args.rs:23-43`
- 问题：旧版分支对每个 token 单独求值，`pop_dangling_flag` 实际不生效；
  且 `Ctx::var` 未提供 `${game_assets}` 等旧变量，展开为空后被删除，
  但其前一个 `--assetsDir` 会残留。
- 触发条件：启动使用 `minecraftArguments` 的旧版本（如 1.6 / 1.7 系）。
- 影响：java 参数错位，旧版本启动异常。
- 建议：旧版分支改为整串切分后统一求值，复用悬空参数清理逻辑，并补齐旧变量。

### M7. 下载中止探测存在队首阻塞延迟

- 位置：`net.rs:299-339`
- 问题：任务按创建顺序合流，计数仅在合流到具体任务时推进；
  若队首为慢任务，其后大量快速失败无法及时触发阈值。
- 影响：镜像故障时中止不及时，用户额外等待；统计数值本身准确。
- 建议：改为按完成顺序处理（如 `FuturesUnordered`），或在任务内使用共享计数器即时判定。

## 低

### L1. 资源哈希切片可能崩溃

- 位置：`install.rs:145`、`install.rs:150`
- 哈希长度不足 2 或非 ASCII 边界时字节切片越界。建议先校验长度与字符集。

### L2. 锁文件内容非法时不清理

- 位置：`launch.rs:166-167`
- 解析失败直接返回，陈旧垃圾锁文件不删除。建议解析失败时一并删除。

### L3. 已存在文件校验失败会整条失败而非重下

- 位置：`net.rs:109-118`
- `file_sha1(dest)?` 的 `?` 会把「无法打开」传播为失败。建议视为校验不通过并重下。

### L4. 其他边界与体验问题

- `launch.rs:324-325`：日志整体读入内存，超大日志占用偏高。
- `net.rs:95`、`net.rs:134`：重试循环在最后一次尝试后仍执行退避等待。
- `net.rs`、`install.rs`、`launch.rs`：异步运行时中混用阻塞式 `std::fs`（当前并发 16，影响有限）。
- `launch.rs:205`：日志文件名为秒级时间戳，同秒两次启动会互相截断。
- `paths.rs:8-10`：环境变量缺失时返回空路径，相对路径会在当前工作目录下建目录。
- `launch.rs:288`：版本列表按字符串排序，`1.10` 会排在 `1.9` 之前（仅显示顺序）。
- `java.rs:91-100`：EA 版本号（如 `22-ea`）首段无法解析，该 JDK 被静默跳过。

## 已检查并确认无问题的区域

- **zip-slip 防护**（`install.rs:231-277`）：`entry.enclosed_name()` 与 `canonicalize`
  前缀校验双重保险，符号链接条目无法借道逃逸。
- **rules 默认值与「最后命中决定」语义**（`args.rs:105-114`）：与官方语义一致。
- **下载中止是否污染统计**（`net.rs:271-320`）：被中止任务不落入任何计数分支，计数无误差。
- **Java 版本号解析**（`java.rs:81-100`）：`1.8.0_504 → 8`、`21.0.12.1 → 21` 等均正确。
- **占位符展开**（`args.rs:142-160`）：未闭合 `${` 返回 `None`，处理正确。
- **`select` / `show_logs` 中的 `unwrap`**（`java.rs:249`、`launch.rs:325`）：均有前置空值判断，不会 panic。
- **`parse_tasklist_pids`**（`launch.rs:125-136`）：内存列中的逗号不影响 PID 解析。

## 建议优先修复

1. **H1** —— 唯一可造成不可逆数据损坏且无需清单校验即可触发的问题，应最先修复。
2. **H2** —— 确定的控制流错误，改动量为一个关键字，收益直接。
3. **M1** —— 补齐元数据校验链，可一并消除远程可控写文件与 L1 的崩溃入口。
   （若更重视离线玩家存档互通，M2 可提升至同档优先级。）
