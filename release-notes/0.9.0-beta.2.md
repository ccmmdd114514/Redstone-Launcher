# 0.9.0-beta.2（Beta 测试版）

发布日期：2026-10-03

版本类型：**Beta 测试版**。此版本修正了 Java 探测的来源判定问题，命令行形态与
beta.1 一致，不含图形界面。

## 本次变更

### 修复

- **Java 来源分级**：此前所有 Java 一视同仁，装在用户目录里的 WorkBuddy 自带 JDK
  与系统 JDK 无法区分，导致误以为「系统 Java 就是 WorkBuddy 的那套」。现在每套 Java
  都会标注来源——`[系统]` 或 `[附带]`。
- **扫描用户级安装目录**：新增 `scan_dirs()`，在原有系统级目录之外一并扫描
  `%LOCALAPPDATA%\Programs\`（含 Java、Eclipse Adoptium、Zulu、Microsoft、
  BellSoft、OpenJDK 等发行商目录）。免提权安装到用户目录的 JDK 不会再被漏掉。
- **选版优先级明确**：`select()` 调整为「系统级精确匹配 → 系统级就近向上 →
  附带级（并打印警告）」。只有系统级完全不满足时才会退到附带级，且会提示
  「卸载宿主应用后启动器会立刻失效」，并建议安装 Eclipse Temurin。
- **doctor 联动自检**：`redstone doctor` 的 `[Java]` 段改为输出来源标签，并在
  「系统级为 0、仅有附带级」时给出显著警告；两个级别均为 0 时提示先安装
  Eclipse Temurin。

### 变更

- `paths.rs` 中常量 `JAVA_ROOT` 更名为 `BUNDLED_JAVA_ROOT`，语义收紧为
  「随其他应用附带的 Java 根目录」，仅作兜底，不再代表本机 Java 根目录。
- Java 列表输出格式调整为 `Java {major} [{来源}] {路径} ({版本})`。

## 相较于上一版的改进

### 修复

- 此前：所有 Java 一视同仁，装在用户目录里的 WorkBuddy 自带 JDK 与系统 JDK 无法
  区分，用户会误以为「系统 Java 就是 WorkBuddy 那套」。现在每套 Java 都标注来源，

- 此前：Java 列表输出格式为 `Java {major} {路径} ({版本})`。现调整为
  `Java {major} [{来源}] {路径} ({版本})`。

验证环境：Windows 11（内部版本 26200），Rust 1.99.0（x86_64-pc-windows-gnu）。

| 系统 JDK 21 在位 | `Eclipse Adoptium\jdk-21.0.12.1+1\bin\java.exe -version` 输出 `openjdk 21.0.12.1 LTS` |
| 系统 JDK 8 在位 | `Eclipse Adoptium\jdk8u504-b01\bin\java.exe -version` 输出 `1.8.0_504` |
| 系统 JDK 已脱离宿主 | Temurin 安装位置为 `%LOCALAPPDATA%\Programs\Eclipse Adoptium`，与 WorkBuddy 自带目录无关，卸载宿主应用后仍然有效 |
| beta.1 遗留 exe 的 doctor | 仅识别到 4 套 WorkBuddy 附带 Java，无一标注为系统级——证明分级逻辑此前未生效 |
| 1.21.8 / 1.21.11 | 版本本体与原生库完整，实例目录 `1.21.11` 存在、`1.21.8` 已缺失，与启动器判定一致 |

> **说明**：beta.2 的源码改动已全部落盘（含 `scan_dirs()`、`classify()`、
> `select()`、`summary()`），但可执行文件尚未重新编译，因此本轮**未对 beta.2 的
> 实际运行输出进行验证**。上述结论来自对 beta.1 可执行文件的复测与源码核对。
> 请在编译出新 `redstone.exe` 后补做 `redstone doctor` 复核。

## 本版本已知 bug 与未解决项

### 本版本新增问题

1. **新 exe 尚未编译验证**：beta.2 的源码改动已全部落盘，但 `dist\redstone.exe`
   仍是 beta.1 的程序。Windows gnu 工具链下 `windows-sys 0.61.2`（raw-dylib）
   调用 `dlltool` 链接时报 `Permission denied`（构建 5 分 11 秒后失败）。
   → 影响：本版说明中的 Java 分级行为**未在 beta.2 的实际产物上验证过**。
   → 当前规避：在纯英文路径 `<用户目录>\redstone` 下手动执行
   `cargo build --release`，把新 `redstone.exe` 复制到 `dist\` 后复核。
2. **`remove` 判据只认实例目录**：`redstone remove <版本>` 仅判定
   `instances\<版本>` 目录是否存在，而 `instances` 命令表格中「实例目录」一列
   只是打印路径、不代表目录真实存在。1.21.8 此前仅保留了版本本体
   （`minecraft\versions\1.21.8`），实例目录已丢失，删除时提示「实例不存在」。
   → 影响：用户会误判为删除功能损坏。
   → 当前规避：删除前先手工确认实例目录是否存在。
   → 计划：将判据改为「版本本体或实例目录任一存在即视为可删」，评估后纳入后续版本。

### 上一版继承未修

1. 仅验证过 1.21.8 与 1.21.11，1.12.2 / 1.16.5 等老版本的兼容分支未实测
   → 计划纳入下一 Beta
2. 无进程锁：重复启动同一版本会因原生库目录被占用而失败 → 计划下一 Beta
3. 无 JRE 自动下载：缺少所需 Java 版本时只提示，不自动下载 → 正式版前
4. 下载无失败阈值：源异常时按重试次数硬扛到底，不提前中止 → 计划下一 Beta
5. 资源索引（`assetIndex`）下载后未校验 sha1 → 计划下一 Beta
6. 仅支持离线账号；微软正版登录与 LittleSkin 尚未实现 → 计划 M2 阶段
7. 不支持模组加载器（Fabric / NeoForge / Forge）与整合包 → 计划 M3 阶段

## 构建与打包方式（-beta.2 起适用）

`dist\` 下的 exe 必须由使用者在**纯英文路径**下构建，中文路径会导致链接器报错。
项目已建立目录联接 `<用户目录>\redstone` 指向本目录，直接在该联接下执行：

```
cd <用户目录>\redstone
cargo build --release
```

随后将 `target\release\redstone.exe` 复制到 `dist\`，再运行

```
python tools\release.py
```

由发布脚本统一打包并写入本说明。
