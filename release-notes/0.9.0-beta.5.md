# 红石启动器 0.9.0-beta.5 发布说明

> Beta 测试版 · 2026-10-04
> 预编译包：本页附件 `redstone-launcher-0.9.0-beta.5.zip`（含 `redstone.exe`、启动脚本与说明文档）
> 源码：本页 Source code (zip / tar.gz) 为 GitHub 自动打包的完整源码快照

## 相较于上一版的改进

### 1. Java 探测：本机明明有 Java 25，启动器却认不出（本版核心修复）

**此前**：只扫描 `JAVA_HOME`、`Program Files` 下的常见厂商目录、注册表与 PATH。
而玩家机器上最常见的 Java 25 来源是**第三方启动器自带的运行时**——本机就是
`%APPDATA%\LabyMod\runtime\java-runtime-epsilon\bin\java.exe`（OpenJDK 25.0.1 LTS）。
这些位置全在白名单之外，于是启动器报告「找不到 Java 25」，而 Minecraft 26.x
（含 26.3）默认要求 Java 25，表现为**装得上、启动不了**。

**现在**：扫描范围扩到 5 类位置，Java 25 能被正常识别：

| 来源 | 具体位置 |
| --- | --- |
| 厂商目录（原有） | `Program Files` 下的 Adoptium / Java / Zulu / Corretto / Temurin 等 |
| 第三方启动器自带 runtime | `%APPDATA%` 下的 LabyMod / HMCL / PCL / BakaXL / PrismLauncher / MultiMC |
| 用户程序目录 | `%LOCALAPPDATA%\Programs` |
| IDE 下载目录 | `~\.jdks` |
| 包管理器 | `~\scoop\apps` |
| 用户自定义 | 环境变量 `REDSTONE_JAVA_DIRS`（分号分隔，兜底用） |

同时修掉两个连带问题：

- **EA 版 Java 识别**：`25-ea` 这类版本号此前解析首段就失败、被静默跳过，现已正常解析。
- **来源分级**：第三方启动器自带的运行时被明确标记为「附带级」，
  选中时会给出警告与失效说明，不会和系统级 Java 混为一谈。

> 明确说明：**仍然不扫描 `%APPDATA%\.minecraft`**。那是游戏自己的目录，
> 需要 Java 的是启动器而不是游戏，扫它只会拖慢启动、误报一堆无效路径。

### 2. 交互方式：从「敲单词」换成「按数字键」

**此前**：双击进去是 `redstone>` 提示符，得自己敲 `install 1.21.8`——拼错一个字母
就报错，对新手极不友好。

**现在**：双击（无参数）直接进**数字键菜单**，按 `1`-`9` 一键直达，
**按下即执行，不需要回车**：

```

  红石启动器
```

- 装版本、启动游戏会先列出候选（最近 9 个正式版 / 已安装版本），同样是按数字选。
- 删除实例改成 `y` / `n` 单键确认，不再要求手打 `--yes`。
- 每一步结束按**任意键**回主菜单，不会刷屏也不会一闪而过。
- 主菜单按 `0` 进入**命令行模式**，原先敲命令的用法原样保留，给进阶用户。

### 3. 彩色终端

**此前**：整屏黑白，成功、失败、警告长得一模一样，得逐字读。

**现在**：红石红作主色，成功绿、警告黄、提示灰，层级一眼可辨。
底层通过 Windows 控制台 API 打开 ANSI 支持（`ENABLE_VIRTUAL_TERMINAL_PROCESSING`），
不额外引入终端库、不依赖第三方 crate。
**输出被重定向到文件时自动退化为纯文本**，不会写一堆 `←[31m` 乱码进日志。

### 4. 字符画图标

**此前**：启动就是干巴巴几行字。

**现在**：启动时用方块字符（`█` / `▓`）画出红石方块图案，配名称与版本号。
纯文本实现，任何等宽字体都能显示，**不依赖任何外部图片资源**，
复制粘贴到聊天窗口也不会散架。

### 5. 全方位汉化

**此前**：帮助文本是 clap 自动生成的**英文**，`redstone --help` 输出一片英文；
安装日志里还混着 `mainClass=...`、`java=...` 这类英文键名。

**现在**：帮助、菜单、提示、报错、进度全部中文，并关闭了 clap 的英文帮助模板，
改为手写中文帮助（`redstone help install` 可单独查某个子命令）。
英文说明文档仍保留在 `README.en.md`，供非中文用户参考。

### 6. 两处高危缺陷修复

- **路径穿越（高危）**：版本号参数未校验就参与目录拼接，`redstone remove "C:\Windows" --yes`
  的预览会指向 `C:/Windows`——`std::path::Path::join` 遇到绝对路径会**整体替换**原路径，
  再加 `remove_dir_all` 就是任意目录递归删除。现已加白名单校验，
  只放行字母、数字与 `. _ - +`，并显式拒绝 `.` 与 `..`，配 2 条单元测试。
- **classpath 截断（高危）**：`install.rs` 遇到 URL 为空的原生库时误写成 `return`，
  会**丢弃其后的全部依赖库与原生库**，现象是「安装显示成功、启动立刻崩」。
  已改为 `continue`，只跳过这一个库。

### 7. 附带级 Java 警告误导用户（探测相关）

**此前**：只要启动时走到了「用附带级 Java」这条分支，就无条件打印
**「系统里没有独立的 Java」**，并把来源写成固定的 `~\.workbuddy\binaries\java`。
本机实际有 System 级的 Java 8 与 Java 21，只是都没有 25 ——
这句话是错的，而且指向的路径也不是真正被选中的那套（LabyMod 自带）。
用户照着这句提示去排查，方向直接跑偏。

**现在**：按「有没有系统级 Java」分两种措辞，且只输出**真正被选中的那一套**：

```
警告：系统级 Java 里没有满足要求的（需要 Java 25），改用附带级的那套：
        Java 25  C:\...\LabyMod\runtime\java-runtime-epsilon\bin\java.exe
        附带级 Java 是别的应用带来的（第三方启动器 / 开发工具自带的运行时），
        卸载那个应用后启动器会立刻失效。
        建议安装 Eclipse Temurin 到 C:\Program Files\Eclipse Adoptium。
```

这个 bug 是新增的探测探针**当场跑出来的**，不是靠读代码看出来的。

### 8. 新增本机验证手段：Java 探测探针

**此前**：本机产不出可执行文件，单元测试只能在 CI 跑。
改了 Java 探测逻辑后，本机完全没法验证，只能等 CI 出结果，一轮就是好几分钟。

**现在**：`tools\probe-java-scan.rs` + `tools\probe-java-scan.py`。
`java.rs` 只用 `std` + `anyhow` + `crate::paths`，不碰 Windows API，
因此能脱离 `windows-sys` 依赖链单独编译。一条命令即可在本机跑真实探测代码：

```
python tools\probe-java-scan.py 25
```

输出全部探测结果（含来源分级）与指定大版本的选版结果。本版的核心 bug
就是靠它在本机实测闭环的（见「验证情况」）。

### 9. 顺带清理

- 日志文件前缀从 `mcl-*.log` 改为 `redstone-*.log`（旧名是改名前的残留），
  同时**兼容读取旧日志**，老用户升级后日志不会「凭空消失」。
- 报错里残留的 `mcl install` / `mcl launch` 全部改为 `redstone ...`。
- 删掉 `launch.rs` 里一个从未被读取的字段，编译警告清零。
- 合并 `Cargo.toml` 中重复声明的 `windows-sys`（原来在 `[dependencies]` 与
  `[target.'cfg(windows)'.dependencies]` 各写了一份）。

## 验证情况

### 构建链路

- GitHub Actions 云端编译（windows-latest 干净环境），沿用 beta.4 已跑通的 workflow。
- 本地 `cargo check --all-targets`：**通过，且代码警告为 0**。
  （`cargo build --release` 在本机仍被 dlltool 权限问题卡住——
  详见「上一版继承未修」第 4 条，与本次代码改动无关。）

### 实测证据（本轮新增）

**Java 探测已在真机跑通，不再只是「理论上应该能认出来」。**

本机 `cargo build` / `cargo test` 会卡在 dlltool（见「上一版继承未修」第 4 条），
拿不到可执行文件。但 `java.rs` 只用 `std` + `anyhow` + `crate::paths`，
不碰 Windows API，因此可以脱离依赖链单独编译。于是新增了
`tools\probe-java-scan.rs` + `tools\probe-java-scan.py`，把**真实的探测代码**
编成探针在本机执行：

```
> python tools\probe-java-scan.py 25

=== 本机 Java 探测结果 ===
  Java 8   [系统] ...\Eclipse Adoptium\jdk8u504-b01\bin\java.exe  (1.8.0_504)
  Java 8   [附带] ...\.workbuddy\binaries\java\jdk8u504-b01\bin\java.exe  (1.8.0_504)
  Java 17  [附带] ...\.workbuddy\binaries\java\jdk-17.0.2\bin\java.exe  (17.0.2)
  Java 20  [附带] ...\.workbuddy\binaries\java\jdk-20.0.2+9\bin\java.exe  (20.0.2)
  Java 21  [系统] ...\Eclipse Adoptium\jdk-21.0.12.1+1\bin\java.exe  (21.0.12.1)
  Java 21  [附带] ...\.workbuddy\binaries\java\jdk-21.0.12.1+1\bin\java.exe  (21.0.12.1)
  Java 25  [附带] C:\Users\cmd114514\AppData\Roaming\LabyMod\runtime\java-runtime-epsilon\bin\java.exe  (25.0.1)

共探测到 7 套 Java

=== 选版测试：需要 Java 25 ===
警告：系统级 Java 里没有满足要求的（需要 Java 25），改用附带级的那套：
        Java 25  C:\Users\cmd114514\AppData\Roaming\LabyMod\runtime\java-runtime-epsilon\bin\java.exe
        附带级 Java 是别的应用带来的（第三方启动器 / 开发工具自带的运行时），
        卸载那个应用后启动器会立刻失效。
        建议安装 Eclipse Temurin 到 C:\Program Files\Eclipse Adoptium。

选中 → Java 25（25.0.1）C:\Users\cmd114514\AppData\Roaming\LabyMod\runtime\java-runtime-epsilon\bin\java.exe
```

**结论：本版核心 bug 已闭环**——此前探测不到的那套 Java 25
（`LabyMod\runtime\java-runtime-epsilon`，OpenJDK 25.0.1 LTS）现在能被识别，
并且 `require(25)` 会把它选出来。

选版策略各分支同样实测覆盖：

| 需要 | 结果 | 是否符合预期 |
| --- | --- | --- |
| Java 8 | 系统级 `jdk8u504-b01` | ✓ 系统级精确命中 |
| Java 21 | 系统级 `jdk-21.0.12.1+1` | ✓ 系统级精确命中 |
| Java 17 | 系统级 Java 21，并提示「未找到 Java 17，改用系统级 Java 21」 | ✓ 就近向上 |
| Java 25 | 附带级 LabyMod Java 25，并给出附带级警告 | ✓ 附带兜底 + 警告 |
| Java 30 | 报错「本机最高只有 Java 25」，附最高那套的完整路径 | ✓ 正确失败 |

自定义目录通道也实测有效：设 `REDSTONE_JAVA_DIRS=D:\mmcc\meta\java_versions`
后，额外识别出 3 套 Mojang 官方运行时（jre-legacy / gamma / delta），
探测总数由 7 套增至 10 套。

**探针当场抓出并修掉一个错误提示 bug**：警告分支原来无条件打印
「系统里没有独立的 Java」，可本机明明有系统级 Java 8 与 Java 21；
而且它把来源写成固定的 `~\.workbuddy\binaries\java`，
与实际选中的 LabyMod 那套对不上。现按「有没有系统级 Java」分两种措辞，
并且只输出真正被选中的那一套。上表 Java 25 那行就是修好之后的实际输出。

### 其他实测证据

- **扫描范围对照**：白名单外另发现 `D:\mmcc\meta\java_versions\`、`D:\Mixly`、
  ARCTIME 自带 JRE 等多套 Java——这些是刻意不纳入的（非标准发行版/与启动无关），
  已通过 `REDSTONE_JAVA_DIRS` 提供手动兜底入口。
- **路径穿越复现**：修复前实测 `redstone remove "C:\Windows"` 预览指向 `C:/Windows`；
  修复后同一条命令被白名单拒绝并给出中文原因。2 条单元测试固化该行为。
- **单元测试**：由 15 项增至 17 项（新增版本名白名单的「接受正常 ID」与「拒绝穿越」各 1 项）。
- **`cargo check --all-targets`**：通过，代码警告 0 条。

### 尚未实测（如实标注）

- **数字键菜单、彩色输出、字符画图标、全方位汉化：只通过编译验证，未实机点验。**
  这几项依赖真实控制台与可执行文件，本轮拿不到 exe，因此没有在真实终端里跑过一遍。
  详见「本版本新增问题」第 1 条。
- **`install 26.3` / `launch 26.3` 端到端未跑通**：Java 25 的探测与选版已在真机验证通过
  （见上），但从「选到 Java 25」到「装完 26.3 并成功进游戏」的完整链路本轮没有实机执行。

## 本版本已知问题与未解决项

### 本版本新增问题

1. **四大新功能未实机点验（本版最大风险）**
   - 现象：数字键菜单、彩色终端、字符画图标、全方位汉化四项，本轮只到
     「源码写完 + `cargo check` 通过」，**没有在真实控制台里运行过一次**。
   - 影响：可能存在排版错位、按键响应异常、部分终端不着色等未预期问题，
     但均不影响既有命令行用法（`redstone <命令>` 一行未改）。
   - 规避：需要稳定使用时，用外部命令行 `redstone install 1.21.8` 这类传统方式；
     或在菜单里按 `0` 进命令行模式。
   - 计划修复版本：0.9.0-beta.6（拿到 CI 产物后逐项实机点验并修复）。

2. **单键读取依赖真实控制台**
   - 现象：`read_key()` 走 Windows 控制台 API，当输入被重定向（管道 / 文件）或
     在非 Windows 终端里运行时取不到按键，菜单会直接退出。
   - 影响：只影响「非真实控制台」这一种场景；正常双击打开不受影响。
   - 规避：用真实 cmd / Windows Terminal 窗口运行。
   - 计划修复版本：待定（可考虑检测到非交互终端时自动降级为命令行模式）。

3. **菜单模式下 `install` 期间无法中断**
   - 现象：数字键菜单选「3 安装版本」后，下载过程中按键无响应，
     必须等本次下载跑完（或失败中止）才能回主菜单。
   - 影响：仅影响体验，不影响正确性；已下好的文件会被缓存跳过，重进不用重下。
   - 规避：等它跑完。
   - 计划修复版本：待定。

### 上一版继承未修

1. **二进制内含构建机源码路径**（beta.4 承诺 beta.5 修复，**本版未修，顺延**）
   - 现象：exe 字符串中可检索到 CI 构建机的依赖源码路径
     （形如 `C:\Users\runneradmin\.cargo\registry\...`），来源为 Rust 的 panic 调试信息。
   - 影响：仅为构建环境信息，不含任何用户隐私，不影响功能与安全。
   - 说明：本版改为中文与交互，改动面已不小；路径裁剪涉及 release profile 调整，
     为避免与本次改动互相干扰，留到 beta.6 单独处理。
   - 计划修复版本：0.9.0-beta.6。

2. **老版本兼容未验证**（beta.4 承诺 beta.5 验证，**本版未做，顺延**）
   - 1.12.2（Java 8）、1.16.5 等新旧分支未实机跑通。
   - 计划修复版本：0.9.0-beta.6。

3. **离线 UUID 未对齐 HMCL / PCL2**（beta.4 承诺 beta.5 处理，**本版未做，顺延**）
   - 当前用 `uuid5("offline:<昵称>")` 派生，与主流启动器的算法是否一致尚未核对。
     不一致会导致同一存档在不同启动器下「人不是同一个人」。
   - 计划修复版本：0.9.0-beta.6。

4. **本机无法产出可执行文件（工具链级问题，非代码问题）**
   - 现象：本机 `cargo build --release` 时，`windows-sys` 需要 `dlltool` 生成
     `kernel32.dll_imports.lib`，而该文件在**子进程写入的瞬间**被安全软件锁住，
     报 `Permission denied`；同一命令手动执行 100% 成功。
   - 已排除：中文路径（改用纯英文 junction 后同样失败）、构建目录位置
     （`D:\Redstone-Build`、`%LOCALAPPDATA%`、WorkBuddy 工作区都试过）、
     沙箱隔离（在沙箱外执行，报错完全一致）。
   - 影响：**只影响本机**，CI（windows-latest，环境干净）不受影响；
     发布包一律由 CI 产出。副作用是本机跑不了 `cargo test`（链接阶段同样卡住），
     单元测试只能在 CI 里验证。
   - 缓解（本版新增）：`tools\probe-java-scan.py` 可以绕开这条依赖链，
     在本机单独编译并运行 Java 探测逻辑，核心 bug 因此能在本机实测闭环。
     但这只救了 Java 探测一块，其余模块（安装、启动、交互）仍只能靠 CI。
   - 计划修复版本：非代码问题，不设版本；后续考虑彻底移除对 `raw-dylib` 的依赖
     （例如改用 MSVC 工具链或换掉引入 `windows-sys` 的传递依赖）来根除。

5. **无 JRE 自动下载**：缺少对应 Java 版本时只提示，不自动下载。计划修复版本：待定。

6. **仅支持离线账号**：微软 OAuth 正版登录与 LittleSkin 尚未实现。计划修复版本：待定。

7. **不支持模组加载器**：Fabric / NeoForge / Forge 与整合包均未支持。计划修复版本：M3。
